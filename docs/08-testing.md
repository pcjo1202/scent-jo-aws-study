# 08. 테스트 전략

개인 프로젝트에 전면 커버리지는 낭비다. **깨지면 치명적인 곳만** 테스트하고 나머지는 쓰지 않는다.

## 무엇이 치명적인가

기준은 하나다. **조용히 깨지면서 학습을 오염시키는가.**

| 대상 | 조용히 깨지면 | 테스트 |
|---|---|---|
| 추출 파서 | 문항이 잘리거나 선택지가 누락된 채로 1019번 학습한다 | **필수** |
| 채점 로직 | 복수정답 123문항의 정오가 뒤집힌다. 통계 전체가 거짓이 된다 | **필수** |
| JWT 가드 | 인증이 뚫린다 | **필수** |
| 기록 정합성 | 옛 오답이 최신이 되거나 시험 중 정오가 새어도 화면은 멀쩡하다 | **필수** |
| CORS 허용 Origin 파서 | 프리뷰 도메인이 조용히 차단되거나, 반대로 남의 Origin이 통과한다 | **필수** |
| 화면 렌더링 | 눈에 즉시 보인다 | 안 씀 |
| API 라우팅 | 즉시 500이 난다 | 안 씀 |

## 1. 추출 파서

### 골든 픽스처

원본 PDF 텍스트에서 **대표 문항 6개**를 뽑아 기대 출력과 함께 고정한다. 아래 성질을 전부 덮는다 — 한 문항이 여러 성질을 겸한다.

| 성질 | 왜 | 문항 |
|---|---|---|
| 단일정답 표준형 | 기본 경로 | 242 |
| 2개 정답 | 109문항 | 44 |
| 3개 정답 | 14문항 | 451 |
| 선택지 5개(E까지) | 복수정답에 자주 붙는다 | 44 |
| 선택지 6개(F까지) · 정답에 `F` | 8문항 | 451 |
| 지문에 줄바꿈이 많은 것 | 열 래핑 오파싱의 주범 | 1 · 494 |
| 선택지가 여러 줄인 것 | 〃 | 1 · 2 |
| 페이지 경계에 걸친 문항 | 푸터가 본문에 섞인다 | 1 · 2 |
| 오답 해설이 정답 개수만큼 빈 것 | `rebuttals` 길이 불일치가 정상인 경우 | 전부 |
| 코드 블록(IAM 정책 JSON) | 한 줄로 접으면 읽을 수 없다. 7문항 | 494 |
| 키만 있고 본문이 다음 줄인 선택지 | 선택지를 통째로 놓친다 | 494 |
| 접힌 요구사항 불릿 | 항목 경계를 복원할 수 없는 경우 (`04` 「파서가 복원할 수 없는 것」) | 494 |

**기대 출력은 원문을 읽고 손으로 적는다.** 파서가 뱉은 값을 붙여넣으면 버그까지 기대값으로 굳는다.

**비교는 공백을 지우고 한다.** 줄 이음매의 공백은 PDF에 정보가 없어 코퍼스 빈도로 추정하는 값이고, 그 정확도는 라벨 1638건으로 따로 측정한다 (`04` 「파서가 복원할 수 없는 것」). 픽스처가 지키는 것은 **구조**다 — 잘림·누락·절 침범·오답 해설의 선택지 재기술 잔류. 줄바꿈은 지우지 않는다. 코드 블록의 줄 구조가 살아 있어야 하기 때문이다.

**픽스처 자체는 저작권 자료다.** `data/`처럼 git에 올리지 않는다. `tests/fixtures/`도 `.gitignore`에 넣고, `pnpm data:pull`이 함께 내려받는다.

### data:verify

전수 검증이다. 테스트 프레임워크가 아니라 스크립트로 돌리고, 실패하면 배포를 막는다.

- 문항 id가 1~1019 연속. 누락·중복 없음
- 모든 문항에 선택지 4개 이상
- 모든 문항에 정답 1개 이상, 정답 키가 실재하는 선택지를 가리킴
- `answer` 길이 1~3
- **정답 개수 분포가 `896 / 109 / 14`와 일치** ← 원본에서 확인한 값. 어긋나면 파싱이 깨진 것이다
- `explanation` 비어 있지 않음
- `rebuttals` 키가 선택지에 존재하고 정답 키와 겹치지 않음
- 노트 186개, 비교 48쌍
- 카테고리 분포 출력 → 눈으로 확인 (한 카테고리가 900이면 별칭 사전 오류)
- 태깅 실패 문항 수 출력

분포 일치 검증이 이 목록에서 가장 강력하다. **하나의 숫자가 파싱 전체의 건강을 증명한다.**

## 2. 채점 로직

`catalog` 모듈의 순수 함수를 테스트한다. DB도 HTTP도 필요 없다.

```ts
grade(selected: ChoiceKey[], answer: ChoiceKey[]): boolean
```

| 케이스 | 기대 |
|---|---|
| `['A']` vs `['A']` | true |
| `['A']` vs `['B']` | false |
| `['A','C']` vs `['C','A']` | **true** — 순서 무관 |
| `['A']` vs `['A','C']` | **false** — 부분정답은 오답 |
| `['A','B','C']` vs `['A','C']` | false — 초과 선택 |
| `[]` vs `['A']` | false — 미응답 |
| `['A','A']` vs `['A']` | false — 중복 선택은 무효 |

순서 무관과 부분정답 불인정이 핵심이다. 실제 시험 규칙과 같다.

추첨도 함께 본다.

- `pickExamQuestions()`가 **정확히 65개**를 반환
- 중복이 없음
- 전부 1~1019 범위

## 3. JWT 가드

| 케이스 | 기대 |
|---|---|
| 유효한 토큰 | 200, `sub`가 `user_id`로 들어옴 |
| 토큰 없음 | 401 |
| 만료된 토큰 | 401 |
| 서명 불일치 | 401 |
| 알 수 없는 `kid` | 401 |
| `iss` 불일치 | 401 |
| `aud`가 `authenticated`가 아님 | 401 |
| `email`이 `ALLOWED_EMAIL`과 불일치 | 403 |
| `/health` | 인증 없이 200 |

JWKS는 스텁으로 대체하고 테스트용 키쌍으로 서명한다. 실제 Supabase를 부르지 않는다.

마지막 항목이 중요하다. 전역 가드를 쓰므로 `@Public()` 예외가 **의도한 경로에만** 붙었는지 확인해야 한다.

## 4. 기록 정합성

2026-08-26 결정(오프라인 큐·advancesPointer·미완료 세션 제외)으로 생긴 경로. 전부 쿼리·순수 로직 레벨이라 DB 스텁으로 충분하다.

| 케이스 | 기대 |
|---|---|
| batch: `answeredAt`이 과거인 항목 재전송 | `created_at`이 `answeredAt`으로 기록 — 이후 시도보다 "최신"이 되지 않는다 |
| batch: 항목 중 하나가 4xx 상당 | 해당 항목만 `rejected`, 나머지는 `saved` |
| `advancesPointer: false` 제출 | `study_progress` 무변화 |
| 진행 중 exam 세션의 시도 | 오답 목록·풀이 상태·통계에 안 나타남. 세션 종료 후엔 나타남 |

## 소유권 검증

가드와 별개로, 남의 데이터에 닿지 않는지 확인한다. RLS가 없으므로 애플리케이션이 유일한 방어선이다.

| 케이스 | 기대 |
|---|---|
| 남의 `sessionId`로 `GET /exams/:id` | **404** (403 아님) |
| 남의 `sessionId`로 답안 제출 | 404 |
| 요청 본문의 `userId`를 토큰보다 우선하지 않음 | 토큰이 이긴다 |

403이 아니라 404인 이유: 존재 여부를 흘리지 않는다.

## 안 쓰는 것

| | 왜 |
|---|---|
| E2E (Playwright 등) | 솔로 개발이고 화면을 매일 직접 본다. 유지 비용이 얻는 것보다 크다 |
| 컴포넌트 스냅샷 | 디자인이 자주 바뀐다. 스냅샷이 전부 깨지고 무의미하게 갱신하게 된다 |
| DB 통합 테스트 | 스키마 제약(check, 부분 유니크 인덱스)이 이미 DB에서 강제된다. 마이그레이션 적용이 곧 검증이다 |
| 커버리지 목표치 | 숫자를 채우려고 의미 없는 테스트를 쓰게 된다 |

## 실행

```
pnpm test          # 위 3종
pnpm data:verify   # 전수 검증. 배포 게이트
```

CI는 두지 않는다. 솔로이고 배포 전에 로컬에서 돌린다. 잊어버리기 시작하면 그때 GitHub Actions를 붙인다.
